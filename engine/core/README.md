# Universal Core — U1.1
First independent Rust library; no production Android integration. F2.2 remains
the Android baseline. See ../../docs/UNIVERSAL_ENGINE_REQUIREMENTS.md and the
distributed-read and evidence RFCs in docs/.

Read-only byte windows with u64 offsets, up to 1 MiB per window, cumulative
per-session read budget, cooperative cancellation at bounded I/O chunks,
explicit errors and no partial success. No external dependencies, unsafe code,
network access, execution, extraction, signing or publishing. Caller provides
an authorized stable source; a path, snapshot, hash or report evidence ID is
not inferred. The window is an input-relative range for future evidence records.
Blocking OS I/O cannot be interrupted by the flag; it is checked between reads.
Budget counts admitted requests even on failure; caller-retained data and total
parallel budgets are not yet managed. No parser, desktop GUI, JNI, SAF bridge,
hash attestation, or scheduler yet.

Tests: cargo +1.85.1 test --locked --offline. Dedicated CI for Linux, Windows
and macOS. Tests use synthetic inputs, a virtual >4 GiB source and a temporary
small file; they do not prove throughput on real multi-GB files or Android.
Future stages: evidence identity and stable source attestation, format probing,
range adapters for archive entries, global scheduler and resource budgets.

## U1.2 candidate — SHA-256 observations
Stream the declared source or one range through the pinned RustCrypto sha2
library, consuming the existing session read budget. No custom cryptography.
The digest describes the bytes actually observed; mutable sources still require
snapshot/attestation policy. A range alone does not prove membership in a
previous full hash. No paths or secrets are exported in this milestone.
Seven additional tests, including standard vectors, chunk boundaries, errors,
cancellation, and range coordinates. The Cargo.lock generated by Linux CI is committed; fetch locked dependencies
and test offline with the same lock on all three operating systems before integration. U1.1's no-dependencies statement describes U1.1 only.

## U1.3 candidate — bounded format hints
Magic-byte triage reads at most 512 prefix bytes and four extra PE signature bytes. No extension-based inference, archive extraction or structural validation. ZIP/APK/JAR/MSIX, OLE/MSI, and ar/DEB remain unresolved container families; CAFEBABE is ambiguous. Ten new tests cover signatures, bounds, malformed pointers, budget, cancellation and truncation. Structural validation, parser capability registry, snapshot identity and provenance remain future work.

## U1.4 candidate — bounded source inventory
Logical source keys separate root scope, relative physical path and nested member paths. Deterministic ordering, duplicate rejection, bounded entry count/path payload, explicit coverage, and consistency between observed length and digest. No automatic filesystem traversal, extraction, absolute paths, SQLite, stable source attestation or report serialization. Logical paths are not safe extraction permissions; case and Unicode aliases are not resolved. Path payload budget does not measure total heap. Eight additional tests.

## U1.5 candidate — bounded parallel batch
Analyze authorized independent stable readers with bounded format probe and SHA-256. All-or-nothing preflight reserves worst-case read bytes, rejects duplicates and caps task count, path payload and worker count. Static round-robin partitions; deterministic key order for completed batch, not deterministic cancellation timing. Cancellation is cooperative; per-item error or cancellation never claims a digest. Thread creation/panic returns a batch error, not a complete inventory. No arbitrary execution, crawling, extraction, JNI, SQLite, adaptive scheduling, throughput claim or absolute RSS guarantee. Caller supplies stable readers; aliases and mutable-source attestation remain unresolved. Nine additional tests.

## U1.6 candidate — scoped orchestration and coverage accounting
Shared admission checks validate the entire scope before any read. Fixed-size chunks reuse the U1.5 worker engine, maintain a single conservative reservation and consolidate all admitted keys into an inventory with per-item status and charged bytes. Explicit complete/with failures/cancelled states; complete means full declared-byte observation, not structural interpretation. Fatal worker errors return no report; no silent success. Scope still capped at 4096 tasks, static workers, caller-supplied readers, no DAG, priorities, retries, checkpoints, persistence, adaptive tuning, JNI or report serialization. Nine additional tests.

## U1.7 candidate — bounded JSON evidence report v1
Local deterministic JSON with explicit scope, summary, per-item format hints, status, SHA-256 and typed error category. Decimal strings for u64, report-local ordinal IDs, path omission by default (caller must choose policy), explicit logical path opt-in; hashes remain identifying metadata. Revalidate public summary/diagnostics before export; byte cap 16 MiB, reject overflow without returning partial JSON. No raw source contents, absolute paths, upload, files, snapshot attestation, code parsing, Markdown/PDF/ZIP or AI integration. Nine additional tests.

### U1.7 independent consumer gate
Synthetic Rust example emits mixed success/failure, omitted/opt-in logical paths, cancelled large-u64 and empty reports. Python 3.12 standard library independently parses UTF-8 JSON with duplicate-key/nonfinite rejection, checks counters, exact integer representation, path policy, escaping, SHA-256 via hashlib and deterministic bytes. CI runs the consumer on all three platforms after locked Rust tests. No additional Rust dependency, no real source contents or external upload. This checks representative fixtures, not formal proof of all possible JSON outputs.

## U1.8 candidate — Rust capability registry v1
Nineteen hint entries including unknown and ambiguous magic, twelve operation categories. Bounded signature hints and generic byte access/hash/evidence export are distinguished from unsupported structural validation, member listing, code/resource interpretation, editing, rebuilding and verification. Execution is outside static core scope. Stable textual IDs are registry identifiers, not format certification or authorization. The registry is Rust-core-only; Android Java functionality is not described. No parser, dispatch, report schema change or external dependency. Eight additional tests.

## U1.9 candidate — bounded ELF and PNG header checks
ELF32/64 both byte orders: magic, class, versions, header size, ordinary table bounds and section-name index; extended numbering unsupported. PNG: signature, first IHDR length/type, dimensions, depth/color pairing, compression/filter/interlace fields and IHDR CRC32. At most 64 bytes per invocation (PNG 33), uses ReadSession budget; malformed, unsupported and I/O/cancellation distinct. HeaderChecked does not imply whole-file validity, image decoding, executable loading or safe content. Registry v2 adds InspectHeader only for ELF/PNG; full validation still unsupported. Standalone API, not yet connected to orchestration or reports. Twelve additional tests including registry regression.

### U1.9.2 candidate — PE, DEX and ZIP header subsets
PE DOS/COFF plus optional magic, section-table range, 90 bytes across two reads; PE32/PE32+ only. Classic DEX 035/037–040 LE: 112-byte header, declared size, map/data bounds and selected table ranges; reverse endian and other versions unsupported; no checksum/signature verification. ZIP first local header or standalone empty EOCD: 30-byte prefix max, size bounds; descriptors, encrypted, ZIP64 and selected newer versions unsupported. No name reading, member listing, central directory traversal, extraction or APK identity. HeaderChecked never certifies file completeness. Registry v3, five header families; full structural validation remains unsupported. Thirteen additional tests; previous unsupported-format test updated to JPEG. No new dependencies or orchestration changes.

### U1.9.3 candidate — opt-in orchestration and JSON v2
run_with_headers uses the same bounded worker pipeline and reserves up to min(declared length,112) extra bytes per item before any read. Header inspection occurs after signature probe and before full hash; malformed/unsupported header does not prevent byte observation. On failed/cancelled items header claims are withheld. Legacy run and JSON v1 retain their previous budget and output semantics. JSON v2 exposes header verdict and typed metadata; validates report accounting and format compatibility, not authenticity. Complete state still means byte observation only. Eight new Rust tests and a sixth independent JSON consumer read per platform. No whole-file parsing or JNI.

## U1.10 candidate — portable metadata-only discovery
Caller-authorized absolute stable directory root with trusted ancestors. Enumerates regular file metadata into ordered logical keys with Unknown/Unexamined coverage; no file content opened. Observed symlinks and Windows reparse points skipped, explicit counters for special files, invalid names and depth exclusions. Global visited-entry/path-payload caps, depth cap 32, cooperative cancellation and atomic errors. Portable path-based walk is NOT race-resistant against concurrent replacement, untrusted ancestors, mount crossings or hard-link aliases. No opening discovered files, automatic analysis, JNI, persistent index or report integration. Eight cross-platform tests plus two Unix tests; Windows reparse handling still needs a dedicated fixture.

### U1.10 portability correction
macOS runner refused the invalid UTF-8 fixture at file creation (OS 92, Illegal byte sequence), before discovery. The actual raw-byte directory entry test is Linux-only; Unix logical-name rejection remains an integration test on Linux/macOS. Shared logical-key conversion now has filesystem-independent unit tests for invalid paths and invalid native encoding (raw UTF-8 bytes on Unix, unpaired UTF-16 surrogate on Windows). No ignored tests, weakened assertions or production behavior change intended. Expected totals: Linux 114, macOS 113, Windows 111.

## U1.11.0 candidate — SQLite schema contract (not runtime)
Prototype strict SQLite schema for transactional run + immutable source rows, explicit seal, status-derived summary, omitted/opt-in opaque logical keys, exact unsigned 64-bit big-endian blobs, 32-byte digest invariant. Seven independent Python sqlite3 tests exercise real temporary database reopen, rollback, incomplete seal, constraints, privacy and status. Foreign keys required per connection; only sealed runs appear in summary view. No production Rust driver, canonical key encoding, resource-budget enforcement across runs, migration, cleanup/deletion, encryption, GUI, source file opening or resume. A trusted future adapter must validate source metadata, enforce path/budget policies and restrict SQL access; database constraints do not establish evidence authenticity or defend against a writer altering the schema.
